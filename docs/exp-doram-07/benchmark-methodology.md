## 1. 方法学（任务 §7）

- **匹配设计**：同一 `(n, T, workload, seed)` 生成的**完全相同**的操作序列喂给 E0 和 E1。E0/E1 只在读取/更新路径上不同。
- **计时**：`perf_counter()`，计时时不启用 `tracemalloc`（后者会使计时膨胀 2–3×，沿用 EXP-DORAM-01-R1 的做法）。
- **硬校验**：每个 cell 的最后一 rep 强制检查 `export_fields()` 逐字段相等、`actual_returns` 相等、E1 不变量成立；任一失败抛 `RuntimeError`，benchmark 不会产出“漂亮但错误”的数字。全部 800 行三标志均为 1。
- **计数器**：抽象参考模型操作计数（history_rows_scanned / shadow_slots_scanned / equality_checks / selection_operations / update_operations / history_append_operations / fetch_count / query_count / update_count），**不是** MPC 门数/通信轮数/R1CS 约束数。
- **参数矩阵**：`n ∈ {16,64,256,1024}`，`T ∈ {64,256,1024,4096}`，全矩阵无缩减；5 种工作负载：uniform / hotspot（80% 打 20% 地址）/ single_hot（80% 打单地址）/ sparse_write（10% 写）/ dense_write（75% 写）。

## 2. 成本分解要点（任务 §7.4）

### 2.1 Query 成本

Query 是 E1 的核心收益点。以 uniform 为例（Query 中位耗时 E0/E1，ms，括号为倍数 E0÷E1）：

| n | T=64 | T=256 | T=1024 | T=4096 |
| --- | --- | --- | --- | --- |
| 16 | 0.175/0.066 (2.66×) | 0.865/0.213 (4.06×) | 3.882/0.868 (4.47×) | 15.242/3.309 (4.61×) |
| 64 | 0.270/0.110 (2.45×) | 2.409/0.444 (5.42×) | 15.629/1.744 (8.96×) | 56.177/6.436 (8.73×) |
| 256 | 0.335/0.297 (1.13×) | 4.002/1.182 (3.39×) | 37.073/4.888 (7.58×) | 188.559/19.873 (9.49×) |
| 1024 | 0.348/1.485 (**0.23×**) | 4.615/5.838 (**0.79×**) | 68.003/23.158 (2.94×) | 627.688/106.464 (5.90×) |

**结论**：当 `T ≫ n`（历史很长、地址域较小）时 E1 Query 快 3–9×；但当 `T ≪ n`（如 n=1024,T=64/256）时 E1 固定扫 n 个槽位反而比 E0 短历史早停更慢（0.23×/0.79×）。这是成本交叉的直接来源。

### 2.2 Update 成本与“成本转移”

影子表把成本从 Query 转移到了 Update：E0 的 update 只是一次 dict 赋值 + 历史追加（中位 0.05–0.84 ms），E1 每次 STORE 要固定扫 n 个槽位（n=1024,T=4096,dense_write 时 update 中位 **71.9 ms**）。因此**“只是把 Query 成本转移到 Update”的质疑在高写入负载下部分成立**：dense_write 的 E1 总耗时优势明显小于 uniform/sparse_write（例如 n=256,T=4096：dense_write 2.60× vs single_hot 4.59×）。

### 2.3 History append 与 Export 成本

两者共用同一追加规则和承诺计算，append/export 耗时基本相同（如 n=1024,T=4096：E0 append 18.57 ms vs E1 17.59 ms）。**Export 不是差异来源**。

### 2.4 总成本与交叉点（E1 更快的 cell 数 / 每 (n,T) 共 5 个）

| n \ T | 64 | 256 | 1024 | 4096 |
| --- | --- | --- | --- | --- |
| 16 | 4/5 | 5/5 | 5/5 | 5/5 |
| 64 | 3/5 | 5/5 | 5/5 | 5/5 |
| 256 | 2/5 | 4/5 | 5/5 | 5/5 |
| 1024 | **0/5** | **0/5** | 5/5 | 5/5 |

全矩阵 63/80 个 cell E1 总成本更低。**交叉点随 n 右移**：n=16 时 T≥256 全面获益；n=1024 时须 T≥1024 才获益。经验上，当 `T ≳ 16·n`（如 16×64=1024，64×16=1024）时 E1 稳定占优；当 `T ≲ n` 时 E1 必败。

代表性总成本对比（uniform，中位 ms，E0/E1）：

- n=16,T=4096：37.78/26.41（1.43×）
- n=64,T=4096：87.37/39.73（2.20×）
- n=256,T=4096：232.03/69.70（3.33×）
- n=1024,T=4096：680.63/193.67（3.51×）
- 反例 n=1024,T=64：22.97/25.36（0.91×，E1 更慢）

### 2.5 抽象计数 vs Python 时间趋势

以 uniform 的 `shadow_slots_scanned / history_rows_scanned` 比值看：

| n \ T | 64 | 256 | 1024 | 4096 |
| --- | --- | --- | --- | --- |
| 16 | 1.59 | 1.20 | 1.11 | 1.08 |
| 64 | 3.72 | 1.51 | 1.13 | 1.10 |
| 256 | 12.27 | 3.54 | 1.53 | 1.20 |
| 1024 | 42.80 | 11.82 | 3.33 | 1.53 |

比值随 `n/T` 增大而增大，且随 T 增大而收敛到 ~1。这与总成本倍数 **不一致**：例如 n=1024,T=4096 时 E1 扫描槽位数是 E0 扫描历史行数的 1.53×（计数上 E1 更多），但 E1 总耗时却只有 E0 的 0.28（快 3.51×）。

**原因（必须诚实记录）**：两个计数器的“单操作代价”不同——E0 扫一行是 Python 列表索引 + 属性访问 + 比较（较慢），E1 扫一槽是整数循环 + 比较（较快，计数器批量累加）。因此**抽象计数只给出工作量维度的复杂度趋势，不能与 Python 耗时做逐项换算**，更不能外推到 MPC 成本。任务要求区分二者，此处明确区分。

### 2.6 哪些结果只能说明算法复杂度、不能说明 MPC 性能

- 所有墙钟毫秒数：均为 CPython 参考模型（含 E0 的明文早停、E1 的整数循环），不是密态执行。
- 抽象计数器：是 Python 层的工作量化，不等于 MPC 乘法门数或通信轮数。
- E1 的 `if j == addr` 在 MPC 中必须算术化为选择器（design.md Q5/Q8），本轮未实现，其真实成本未知。
- 因此本报告只能支撑“在参考模型与算法结构层面，n/T 较小且 T 较大时双结构有端到端收益”，**不能**支撑“在 VDORAM 的 MPC/SNARK 中该收益成立”。
