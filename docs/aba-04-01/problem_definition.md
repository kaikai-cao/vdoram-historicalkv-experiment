# ABA-04-01 — 独立研究问题定义：执行事件完整性与跨证明同执行绑定

> 工作标签（Working label）：**Execution Event Completeness and Cross-Proof Execution Binding**
> 本文只建立与具体系统无关的抽象模型。VDORAM 仅作为问题来源与历史案例，不进入本文定义。
> 证据等级：`CONSTRUCTED`（本文的定义/关系/游戏均为本轮提出，不代表创新性或可实现性已成立）。

---

## 0. 定位与边界

本轮把研究问题从 VDORAM 的 C#/Rust 接口中抽离出来。三点边界先固定：

1. **不预设每步产生事件。** 事件生成规则是应用语义，不是执行模型的固有部分。某些系统每步产生事件（如旧案例中的访存取证），某些系统只在特定操作产生事件，某些系统根本不要求完整事件序列。
2. **应用不要求记录的步骤，其"缺席"不是遗漏。** P2 completeness 只在相对于一个明确、verifier 可信获知的"必须事件步骤集合"时才有意义。
3. **本文定义的是密码学性质，不是部署方案。** verifier 是否独立、VK 是否固定、T 从哪来，属于部署信任假设（见 §6），与 P1–P5 的证明层语义严格区分。

## 1. 抽象对象

| 对象 | 记号 | 定义（与系统无关） |
| ---- | ---- | ------------------ |
| 程序 | `P` | 固定的计算规范；其身份 `program_id` 由 verifier 侧确定（部署假设，非本文定义内容） |
| 执行 | `Execution` | 在程序 `P` 上从初始状态到终止状态的一次有限运行 |
| 步骤 | `Step_i` | 执行的第 i 个原子转移，索引 i ∈ `[0, T-1]` |
| 状态 | `s_i` | 步骤 i 处或之后的执行状态；转移 `s_i = δ(s_{i-1}, in_i)`（i ≥ 1） |
| 事件 | `Event` | 由某个步骤依据应用语义产出的记录，形如 `e = (step, type, payload)` |
| 执行证明 | `π_exec` | 证明执行满足关系 `R_exec` 的密码学证明 |
| 事件证明 | `π_event` | 证明事件序列满足关系 `R_event` 的密码学证明 |
| 公开锚点 | `Public anchor` | 两份证明共同引用的公开值集合：`eid, T, program_id, D_exec, D_event` 等 |
| 验证者 | `Verifier` | 独立于证明者、仅凭公开输入与证明做判断的主体 |

### 1.1 符号

```
T                  : 总执行步骤数（含 step 0），verifier 需可信获知或由受约束计数器产生
last_step_index    : 最后一个实际执行的 step 索引 = T - 1
[0, T-1]           : 全部执行步骤索引域
E*                 : 真实执行按应用语义产生的事件序列（自然语言中的"真相"）
E                  : 证明者提交并经 π_event 证明的事件序列
D_exec             : 执行证明关联的摘要（如 trace/最终状态承诺），公开
D_event            : 事件证明关联的摘要（如事件序列承诺），公开
eid                : 一次执行的唯一标识
```

### 1.2 事件序列的形式化约定（序列 / 多重集 / 唯一映射）

以下约定直接服务 P1–P5 的书写，用于消除"用集合记号无法区分重复事件"的歧义：

```
E, E*   : 均为有限事件序列 E=(e_1,...,e_N)，N=|E|；序列既保留顺序，也保留重复项。
step(e_j): 序列第 j 项携带的 step 标注。
⟦E⟧     : 由序列 E 忘掉顺序、但保留重复次数所得的有限多重集（multiset）。
{ · }   : 普通集合记号，会合并重复项——P1/P2 的"包含/覆盖"不得用它书写。
f       : 从 S_req 到 E 下标的映射 f(i)=j，含义见 P2。
```

- 由于 `φ` 是函数且 `E*` 按 step 排序，`E*` 中每个 step 至多对应一个事件，即 `step` 在 `E*` 上注入。
- 因此"重复同一 step 的事件"必然不属于 `E*`：它要么违反 P1（多重集包含 `⟦E⟧ ⊆ ⟦E*⟧` 不成立），要么违反 P2（唯一映射 `f` 的覆盖性/单射性不成立）。这是 T2（复制事件）能被严格拒绝的形式化依据。

## 2. 应用级事件生成策略（关键区分）

定义应用策略函数：

```
φ(i, s_{i-1}, s_i, in_i) → Event | ⊥
```

- `φ` 由应用语义给出，决定步骤 i 是否必须产生事件、事件类型与内容。
- 定义 **必须事件步骤集合** `S_req ⊆ [0, T-1]`：应用要求 `∀ i ∈ S_req, φ(...) ≠ ⊥` 的步骤集合。
- `E* = sort_by_step({ φ(i, ...) | i ∈ S_req 及所有 φ 产出非 ⊥ 的步骤 })`，按 step 严格排列。

三种典型策略（仅举例，不穷尽）：

| 策略 | `S_req` | completeness 的含义 |
| ---- | ------- | ------------------- |
| 全步骤取证 | `[1, T-1]`（step 0 通常不产生） | 每个要求步骤都不能少 |
| 条件触发 | 仅满足某 opcode 条件的步骤 | 只要求触发步骤产生事件；非触发步骤无事件是正常 |
| 只记录部分 | 应用显式指定的子集 | 未指定步骤的缺席不算遗漏 |

**推论**：脱离 `S_req` 谈 "事件完整性" 是无定义的。任何 P2 论断必须先固定 `S_req` 及其可信来源。

## 3. 证明关系（抽象）

```
R_exec(w_exec, D_exec, T, program_id) = 1   —— π_exec 证明之
R_event(w_event, D_event, E) = 1            —— π_event 证明之
```

- `w_exec`：执行 trace、状态、输入等私有 witness。
- `w_event`：事件生成依据（step、type、payload、以及来自执行的私有中间量）等私有 witness。
- verifier 可见：`program_id, eid, T, D_exec, D_event`（公开锚点）、`E`（事件明文或其承诺）、`π_exec, π_event`。
- verifier 不可见：`w_exec, w_event` 内部值。

**核心结构性事实**：`π_exec` 与 `π_event` 是两个独立证明，各自的 soundness 只保证"相对自身 statement 自洽"。二者是否描述同一次执行，不是任一单独 soundness 的产物——这正是 P4 要形式化的缺口。

## 4. 安全性质 P1–P5

记号：`Accept` 表示 verifier 接受一对证明；攻击者 = 恶意证明者，可任意选择 witness 与事件序列，但不能破坏底层证明系统的 soundness 与承诺的 binding（这些列为假设）。

### P1 — Event soundness（事件可靠性）

- **精确定义**：`Accept ⇒` 每个被接受的序列项 `e_j ∈ E` 都能在真实执行中找到唯一来源步骤 `i`，使 `e_j` 与 `φ(i, ...)` 一致。按多重集写为 `⟦E⟧ ⊆ ⟦E*⟧`（**多重集**包含，保留重复次数），即 `E` 中任一事件的重数不超过其在 `E*` 中的重数。禁止用集合 `⊆` 记号——那会把重复项合并，使伪造的重复事件通过。
- **攻击者能力**：伪造事件内容/类型/绑定 step；令 `E` 中出现 `E*` 之外的事件；或复制 `E*` 中已有事件使其重数超过真实值（此类由 `⟦E⟧ ⊆ ⟦E*⟧` 的重数比较拒绝）。
- **verifier 可见**：`E`、`D_event`、公开锚点；执行 trace 与状态为私有。
- **必要假设**：`R_event` 的 soundness；若事件内容依赖执行私有状态，需执行侧对该状态的绑定承诺，否则 `R_event` 无法独立验证内容真实性。
- **成功（攻破）**：verifier 接受了某个 `e ∉ E*` 的事件。
- **失败（被阻断）**：任何被接受的事件都可归约到执行中的真实来源步骤。

### P2 — Event completeness（事件完整性）

- **精确定义**：`Accept ⇒` 存在**唯一映射** `f : S_req → E`，满足：
  - **覆盖性**：`∀ i ∈ S_req, ∃ e ∈ E, step(e) = i`（每个要求步骤都有事件）；
  - **唯一性**：`f` 是单射且良定义——`∀ i ∈ S_req, ∃! e ∈ E, step(e) = i`，即每个要求步骤**恰好**对应一个事件，既不少也不重。
  - 在 P1 成立时，`f(i)` 与 `φ(i, ...)` 一致。
  - 注意：不能用集合 `{ step(e) | e ∈ E } ⊇ S_req` 书写——集合中重复 step 只算一个元素，某个必需步骤的事件被复制时该式仍成立，无法支撑唯一性。必须用序列/多重集上的唯一映射 `f`。
- **攻击者能力**：省略 `S_req` 中某些步骤的事件（提交更短的 `E'`）；或复制某个已要求步骤的事件，使 `step` 不再注入（集合写法对此无感，唯一映射写法拒绝）。
- **verifier 可见**：`E`（作为序列，可逐项读 step）、`T`、`S_req`（策略须 verifier 可信获知）。
- **必要假设**：`S_req` 是应用层可信输入（非 prover 自报）；`T` 可信（见 P5）；需在证明关系中约束 `f` 的覆盖性与单射性——例如每步事件生成约束 + `step` 注入性（lookup/argument 证明 `∀ i ∈ S_req, ∃! e`）。
- **成功（攻破）**：verifier 接受缺少某要求步骤事件、或某要求步骤有重复事件的 `E`。
- **失败（被阻断）**：唯一映射 `f` 存在（覆盖且单射）。
- **边界**：应用不要求的步骤缺席，不构成对 P2 的违反。

### P3 — Event ordering（事件顺序）

- **精确定义**：`E` 按 step 严格递增，且其顺序等于真实执行顺序（`E` 与 `E*` 保序等价）。
- **攻击者能力**：在保持事件集合不变的前提下重排事件。
- **反例（说明 P1+P2 不蕴含 P3）**：`E*=[e₁(1), e₂(2), e₃(3)]`，提交 `E=[e₁(1), e₃(3), e₂(2)]`。P1（每个 e 真实）、P2（覆盖 step 1/2/3）均成立，但顺序错误。
- **verifier 可见**：`E` 中事件的 step 字段；需能检查提交顺序与 step 顺序一致。
- **必要假设**：step 来源可信（依赖 P5 的受约束计数/可信终止）；单纯检查 prover 自报 step 的单调性不足。
- **成功（攻破）**：verifier 接受非按真实 step 顺序排列的 `E`。
- **失败（被阻断）**：顺序约束在证明关系中成立。

### P4 — Cross-proof execution binding（跨证明同执行绑定）

- **精确定义**：`Accept ⇒ π_exec` 描述的执行 `Exec₁` 与 `π_event` 中事件所归属的执行 `Exec₂` 为同一次执行。形式化：不存在 `(w_exec, w_event)` 使 `π_exec` 有效对应 `Exec₁`、`π_event` 有效对应 `Exec₂`、公开锚点字段全同，但 `Exec₁ ≠ Exec₂`。
- **攻击者能力**：完全控制两组 witness 与两份证明，令其对应不同执行，却共享 `eid`、`D_exec`、`D_event` 等公开字段。
- **verifier 可见**：两份证明与公开锚点；两组私有 witness 均不可见。
- **必要假设**：需要 **linking relation**——两份证明都在各自电路内约束同一个（可信来源的）摘要/承诺，且该承诺 binding、witness 与承诺的对应关系以 opening 证明。**相同 `eid` 字符串或相同摘要字段本身不是 linking relation。**
- **成功（攻破）**：verifier 接受两个不属于同一次执行、但共享公开字段的有效证明。
- **失败（被阻断）**：任何被接受的对都可归约到同一执行的同一组 witness。
- **推论**：递归证明若仅验证"两个子证明各自有效"，不能解决 P4；除非递归电路额外约束两子证明的公开摘要相等且这些摘要 binding 到各自 witness。

### P5 — Termination binding（终止绑定）

- **精确定义**：`E` 的完整性覆盖到真实终止位置，且 `T` 等于真实执行的终止步数，而非 prover 自报。事件最大 step 与 `T-1` 的关系由 `S_req` 策略确定。
- **攻击者能力**：声明 `T' < T`（前缀截断）或 `T' > T`；用 `expected_step_bound` 上界冒充实际 `T`。
- **verifier 可见**：`T`（公开，但来源须可信）、可能的 halt 公开输出、公开锚点。
- **必要假设**：`T` 来自 verifier 固定/可信来源，或受约束计数器（`step₀=0`、`step_{i+1}=step_i+1`、halt↔末项绑定）。**`count(E)=f(T)` 不能单独锚定 `T`**——若声明更小的 `T'`，计数关系同样自洽。
- **成功（攻破）**：verifier 接受基于错误 `T` 的完整性声明。
- **失败（被阻断）**：`T` 与真实终止绑定，截断与超长均可被拒。

## 5. 性质间依赖

```
P5 (可信 T) ──→ P2 (覆盖域 [0,T-1] 需可信 T) ──→ P3 (step 顺序需可信来源)
     │
     └──→ P4 (exec/event 摘要须对应同一 T/执行)

P1 是 P2/P3 的前置（先保证提交的事件都真实，完整性才有意义）
P4 是横切约束：即便 P1/P2/P3/P5 各自成立，若两证明 witness 无关，整体声明仍不成立
```

- P5 是 P2/P3 的前置：不确定可信 `T`，覆盖域与顺序无从定义。
- P1 是 P2/P3 的前置：若事件本身可伪造，完整性与顺序无意义。
- P4 横切：即便 P1/P2/P3/P5 分别成立，两份证明若描述不同执行，整体声明仍为假。

## 6. 三类边界的严格区分

| 类别 | 内容 | 是否可由证明关系解决 |
| ---- | ---- | -------------------- |
| **密码学安全性质** | P1–P5：事件来源、完整性、顺序、同执行绑定、终止绑定 | 是——依赖证明关系实际约束 + 底层 soundness/binding |
| **系统部署信任假设** | verifier 独立性、VK 固定与分发、`program_id` 来源、`T` 可信来源、`eid` 生成方、`S_req` 可信获知 | 否——这些是外部信任根，证明关系只能消费、不能自证 |
| **应用层事件生成策略** | 哪些步骤必须产生事件、事件类型定义、是否要求完整性、`S_req` 的具体取值 | 否——由应用语义给定，不能由证明系统代劳 |

**常见混淆及排除**：

- "进入 proof statement" ≠ "来源可信"：公开字段在 statement 中，只说明 verifier 会检查证明相对该字段自洽，不说明字段值来自可信方。
- "相同 `eid`" ≠ "同一执行"：见 P4。
- "hash chain / 签名完整" ≠ "事件内容完整"：链保证顺序/包含关系，不保证链上每项与真实执行一致。
- "计数 `count(E)=T-1`" ≠ "完整"：见 P5。

## 7. 非目标（本文明确不做）

1. 不修复、不适配 VDORAM 的 C#/Rust 接口。
2. 不假设每个执行步骤都产生事件。
3. 不把上界 `expected_step_bound` 当作实际 `T`。
4. 不把相同公开字段、hash chain、签名或递归证明本身当作 P4/P5 的证明。
5. 不声称 P1–P5 已有或没有可证明构造——这是后续 Phase 3/5 的工作。

## 8. 小结

本文给出一组与系统无关的对象、符号与安全性质定义。核心判断是：**P1–P5 的成立依赖于证明关系实际约束的语义，而非 verifier 对某些公开字段的信任；其中 P4（跨证明同执行绑定）与 P5（终止绑定）是最容易被"字段相同/计数相等"误判为已解决、实则最需要显式密码学 linking 的两项。** 后续 Phase 2 将核查现有工作是否已解决这些性质，Phase 3 比较候选构造，Phase 5 据此立项决策。
